# Viva notes: player controller (Systems Engineer, step Y2)

PR #18. Commits d91fe69, 2135c27, 6f21e4c, 3e66fe9 and 9610901. Numbers are in `docs/reference/systems-engineer.md`
sections 1–6.

## What I built

- **Movement code split in two:**
  - `PlayerMovementSettings` (ScriptableObject, every number) and `PlayerMovementLogic` (static, pure): target
    speed, acceleration, the jump and the sprint rule.
  - `FootstepTracker`, `HeadBob` and `LandingSpring`: small classes with no Unity objects, so all of them are tested
    in EditMode.
- **The components:**
  - `PlayerInputReader`: the only class that touches the Input System, using `PlayerControls.inputactions`.
  - `PlayerLook`: yaw on the body, pitch on the pivot, cursor lock.
  - `PlayerMotor`: `CharacterController` movement, ground snap, jump, gravity, footsteps and noise.
  - `PlayerCameraEffects`: bob, landing dip, strafe roll and step smoothing.
- **`Blackout/Systems/Build Player Prefab`.** It generates `Player.prefab` and the settings asset. The hierarchy is
  Player › CameraRig › CameraPivot (eye 1.63 m) › PlayerCamera › WeaponHolder.
- **`Blackout/Debug/Teleport To Checkpoint`**: a Play-mode window with one button per `Checkpoint` marker.
- **20 `PlayerMovementLogicTests`.**

## Why this design

- **Numbers from the prototype, not tuned by feel.** The team agreed on how the browser prototype feels, so walk 4.3,
  sprint 7, gravity 17, jump 5.6, FOV 72° and 0.12° per pixel are copied from its code. Every value can be traced.
- **Logic separate from MonoBehaviours.** That makes it testable in EditMode, which is fast and deterministic.
  PlayMode tests with a scene would be slow and flaky for maths like this.
- **One input reader.** A key change never touches the movement code, and the other systems read the same input.
- **`CharacterController`, not a Rigidbody.** Movement is direct and predictable, and steps and slopes come built in.
  It also costs nothing in the physics step (Y7: 1 dynamic body in the whole game).
- **Footsteps by distance, not time.** Walking into a wall makes no footsteps.
- **The prefab is generated by a tool.** The wiring is recorded in code, the tool can be re-run, and it can be reviewed
  in a PR.

## Alternatives rejected

- **The `PlayerInput` component with SendMessage.** It calls methods by string through reflection.
- **A Rigidbody player.** Friction, bouncing on steps and tuning drag for the prototype's exact accelerations.
- **A hand-built prefab.** Nothing records how it was wired.

## Numbers

- **Ground snap** 0.35 m, a SphereCast at 0.95 × the radius. **Slope limit** 49° = atan(1.15), from the
  prototype's rise/run test.
- **Eye** 1.63 m = 1.75 − 0.12.
- **Landing spring** stiffness 120, damping 14, so ζ = 14 / (2√120) ≈ 0.64.
- **Footstep noise** follows a curve through the prototype's points (0, 0), (4.3 m/s, 4.5 m) and (7, 13), so slow
  walking is quieter [GUESS: the playbook asked for "scaled by speed"].
- **Tests:** EditMode 488/488 (20 new). The builder built the prefab on its first run and left it unchanged on its
  second.

## Known weaknesses

- No crouch, flashlight, pause menu or sensitivity slider (playbook "Could"s).
- At most one footstep per frame. Moving platforms aren't supported.
- The prefab tool can't update an existing prefab: delete the prefab to rebuild it. Later builders add to it instead.
